## Фотографии

Все 40 исходных JPEG и 40 студийных PNG сохранены побайтно. Их хеши, хеш ярлыка и прежних защищённых серверных файлов проверены. Названия, цены, ассортимент, палитра, шрифты, секции и существующие анимации не менялись.

Добавлены 738 производных файлов WebP и AVIF для 80 фотографий в `public/photography/optimized/`. Студийные размеры: 160, 360, 640, 960 и 1122 px по ширине. Для исходных фотографий размеры ограничены реальным разрешением, без увеличения. Максимальный размер 1440 px используется только у достаточно крупных исходников. WebP quality 86, AVIF quality 63 с цветовой субдискретизацией 4:4:4. Размеры не достигались ценой искусственного ограничения веса.

Это сравнение наборов для доставки. Размер проекта на диске увеличился: мастер-файлы специально не удалялись. Страница загружает один подходящий вариант, а не все размеры и оба формата.

Компонент `Photograph` использует нативный `picture`: AVIF с WebP fallback, `srcSet` и `sizes`. Размеры отдельно заданы для hero, каталога, галереи, миниатюр, корзины и фотоленты. Атрибуты width/height и прежняя CSS-геометрия сохраняют место под изображение. Только главное фото hero имеет eager/high; второе фото и карточки используют lazy/auto. На карточке товара крупное фото также имеет высокий приоритет.

Встроенные маленькие blur-превью не требуют HTTP-запросов. Фотографии видимы в серверном HTML и при отключённом JavaScript. После загрузки второстепенных изображений возможен мягкий переход непрозрачности за 180 мс; задержки перед показом нет. Главное фото показывается сразу. При reduced motion этот дополнительный эффект отключён.

Полный каталог теперь присутствует в HTML статической сборки. Раньше короткая заглушка заменялась всем каталогом после запуска JavaScript. Query bridge сохраняет переходы в выбранную категорию, а полноценный fallback убирает этот скачок. Изменение касается доставки, итоговый дизайн тот же.

Playwright + установленный Edge, CDP: 390×844, DPR 3, загрузка 1,6 Мбит/с, отдача 0,75 Мбит/с, задержка 150 мс, CPU ×4, новый контекст, кеш отключён. Для каждой страницы по три запуска. Значения ниже - медианы. Сравнивались статические сборки; прежняя сборка дополнительно воспроизведена из коммита `3bfb483f99e943de53a7bf18c73ffbc977f71ba0`.

LCP главной сократился примерно в 17,4 раза, готовность видимых фото - в 9,3 раза. Передача изображений снизилась на 99,1% на главной и 99,0% в каталоге. LCP каталога не улучшился: разница около +0,13 с. Сам LCP не описывал минутное ожидание фотографий в прежнем каталоге. Поэтому готовность фото измерена отдельно.

Вес изображений включает нативный lazy-буфер браузера рядом с первым экраном. Это не полный вес страницы и не вес всех 40 товаров. Количество HTTP-запросов изображений без прокрутки: главная 4 до и после, каталог 8 до и после. Встроенные data-URL placeholder исключены из HTTP-счётчиков в окончательном `performance-after-http.json`.

Первичный `performance-before.json` ловил в каталоге момент до появления карточек и потому не годится для оценки готовности фотографий каталога. Для этой строки используется повторный `performance-before-catalog-settled.json`, где сначала ожидается появление карточек. Ранние сырые записи сохранены, не исправлялись задним числом. Итоговые данные после оптимизации: `performance-after-http.json`. Дополнительные диагностические записи не используются как независимые сравнения.

Это лабораторные замеры конкретной машины и профиля, не полевые Core Web Vitals и не результат Lighthouse. Отдельный замер опубликованного сайта сохранён в `performance-public.json`; его показатели нельзя напрямую смешивать с локальным сравнением из-за другого сервера, сжатия и CDN.

Медианы отдельной проверки публичной версии при том же мобильном профиле: главная LCP 1,308 с, фото готовы за 2,550 с, CLS 0,0668; каталог LCP 1,428 с, фото готовы за 2,382 с, CLS 0,0799. Это дополнительные замеры текущей публикации, не база для заявления об улучшении относительно старой публичной версии.

Студийные PNG хранятся в публикации по старым адресам для сохранности, но интерфейс их больше не скачивает. Дополнительный Telegram-бот, приём платежей и изменение юридических данных не входят в эту оптимизацию.
